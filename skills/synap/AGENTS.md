# Maximem Synap: agent rules (single-file edition)

This file is **self-sufficient**: copy it alone into `AGENTS.md`, `.cursor/rules/synap.mdc`, `CONVENTIONS.md` or `.clinerules`. Wording: the files in "Where the detail is", or install the full skill (`npx skills add maximem-ai/maximem_synap_sdk --skill synap -y`), whose `SKILL.md` is then the source of truth.

**Never guess. If anything is unclear, stop and ask the human. Never ask the human to paste a key into chat.**

## Start (ask which applies)

- **One-time code** (`syn_ob_...` in the prompt): from step 1. **No code:** a fresh dashboard prompt, or `<cli> auth login` once (the human approves in the browser), then step 2.
- **Already has an instance and a runtime key, or reuses one from step 2b:** skip sign-in, use-case, create and wait (unless still being built); mint the key as in step 10 if `.env` has none, else read it from the environment or `.env` (if missing, name it and have them add it). Read B2C or B2B from whoami (`user_context_isolation`: `equals_customer` is B2C, `strict` is B2B), then Step 0, identity, depth, integrate, verify.

`<cli>` means `maximem-synap` from PATH if `maximem-synap --version` is 0.3.2 or newer, else `npx @maximem/synap-cli@latest` (Node and Python 3.10+). If the prompt names an environment add `--env <name>` to every command. Put `--json` or `--output json` before the subcommand. If `SYNAP_API_KEY` is set in your shell run CLI commands with `env -u SYNAP_API_KEY`.

## The steps

1. Sign in: `<cli> auth login --code <syn_ob_...> --agent-name <claude-code|cursor|codex|windsurf|other>`. A missing, expired or used code is the one case to say "copy a fresh prompt from the dashboard".
2. `<cli> onboard status` shows the WORKSPACE, not this session. Trust only steps you reported yourself in this session; another session's steps are someone else's work: never skip drafting, approval or creation because they look done. Safe to re-run.
2b. **What exists:** `<cli> instances list --json`; tell the human in plain words each instance (name, what it is for if known, ready, being built or failed: see the glossary). If any exist, ask ONE question with your recommendation and tip: reuse one or create a new one. Recommend reuse only if it is for THIS agent (one instance serves one agent).
3. **Step 0, learn Synap first:** read in full https://docs.maximem.ai/getting-started/quickstart.md, /concepts/memory-model-cheat-sheet.md, /concepts/memory-scopes.md, /concepts/how-ingestion-works.md, /concepts/retrieval-modes.md, /concepts/real-time-anticipation.md and your framework's /integrations/<name>.md. Tell the human four lines on what you understood (scoping, the three operations, the live stream, the build/ready rule).
4. Read the repo; infer only what the code supports.
5. One question at a time, showing evidence and still asking. EVERY question carries **my recommendation** (what you suggest and why, from the repo) and a **tip** (how Synap uses the answer and what it changes; write it only after reading the docs page named for that question in `onboarding-ask-rules.md`). Questions: **which agent gets memory now, if the repo has more than one agent** (one instance serves one agent, /concepts/agent-topologies.md; others need their own later); B2C or B2B (chosen when the instance is created); **what identifies a returning person (a stable user id)**; compliance and sensitive data (read /guides/pii-protection.md for health, financial or children's data); what to remember; what never to store. Never use a per-session id as `user_id` unless the human confirms there is no persistent identity, then say plainly that returning memory, profile and per-person erasure are lost; a shared-device id leaks between people.
6. **Choose the integration path. Always use the SDK, never raw HTTP calls.** The implicit path (the live stream: the app reports events and Synap works as they flow) is the DEFAULT for any app that can run a long-lived process (server, worker, container, voice or desktop agent); never present it as optional. Say first what it gives (docs-backed): context prepared before the agent asks, turns recorded with no write calls, delivery that survives dropped connections. Then confirm, default yes: "I will wire the live stream so you get X, Y, Z. Tell me if you do not want it." Implement it FULLY unless the human EXPLICITLY says no ("I do not know" or silence = implement); if they say no, record the one-sentence consequence, use the explicit path (`conversation.record_message` + `fetch`) and report it. On serverless, Edge or short-lived hosts say in one plain sentence it needs a long-lived process (/concepts/grpc-vs-rest.md) and is not available there, use the explicit path with the production rules, and add one neutral sentence that it becomes available if the app ever runs one; do not pitch re-architecting. Check dependency conflicts (protobuf) first. Report `onboard report integrating in_progress --detail "path=implicit|explicit-no|explicit-host"`.
7. Draft the use-case from `<cli> instances template`, every unanswered field literally `not stated`. Show the exact file in full, quote its `shasum -a 256`, upload exactly that file (once sent, it can only be changed by making a request through email to gaurav@maximem.ai: say so), ask again after any change, then `onboard report use_case_drafted done` and, after an explicit yes, `use_case_approved done`.
8. Say the build usually takes 15 to 20 minutes and get a yes (ask before create): `<cli> instances create --name ... --relationship b2c|b2b --from-file usecase.md`. A 409 `instance_name_taken` means the name is in use: say so plainly and ask whether to reuse that instance or choose another name. Do not wait.
9. Integrate. **Done means:** the READ is wired into the model prompt (write-only is not done; say where) and memory informs while the app's own rules decide; writes init the SDK once, set timeouts at init (about 5 s; the SDK has no per-call timeout), enforce the total deadline in the app (`asyncio.wait_for` or a worker thread), use bounded retries, never block the user turn if avoidable, never swallow a failure silently, and you say what is lost on failure; redaction is tested against the never-store list with realistic samples; OFF-safe with one startup log line saying ON or OFF; no staging key in production; versions pinned; `.env.example` and README updated; tests for Synap failing, the 409 path and redaction. Open each call's /sdk-reference page before and after writing it; print a **"Docs read"** list of pages you actually opened (/guides/production-checklist, /patterns/graceful-degradation, /sdk-reference/errors and each method page used) before verifying.
10. `<cli> api-keys create -i <id> --write-env`, then `onboard report env_written done`. Never print or commit the key. One key per instance: if the project will have more than one Synap instance (ask when unsure) add `--env-suffix NAME` (CLI 0.3.2+; after the instance or agent; letters, digits, underscore), which writes `SYNAP_API_KEY_<NAME>` and `SYNAP_INSTANCE_ID_<NAME>`; never save several as plain `SYNAP_API_KEY` (the CLI refuses with exit 6 unless `--force` or a suffix). The app must read the matching variable and pass it explicitly (`sdk-setup.md`, "Several instances"). Run the project's tests with `env -u SYNAP_API_KEY` until verify passes.
11. Run `<cli> instances wait <id>` in the BACKGROUND (log file; poll it). No ingestion or retrieval, including `verify_synap.py`, before it reports ready. A refused call is HTTP 409 `instance_not_ready`: newer SDKs raise `InstanceNotReadyError`, older ones (including 0.5.16) a `ConflictError` saying the memory architecture is still being built; handle both, typed first, wait the stated time, never loop inside the call.
12. Run `SYNAP_VERIFY_REQUIRE_STREAM=1 python scripts/verify_synap.py > verify.out 2>&1; echo "exit=$?"` (no prefix if the host cannot run the stream; `--suffix NAME` for a suffixed key; scripts: raw URL below) and paste verify.out unedited, WARN lines included; it ends with `RESULT:` and `EXIT CODE:`. Run `scripts/check_integration_wiring.py` and drive the app's own endpoint with a sentinel. Every test or probe user id you create (project tests, sentinel, verify) is `test_user_<purpose>_<8 random chars>`: write each down. Before announcing run `python scripts/cleanup_test_data.py --user-id <id> ... --dry-run`, then without it, for exactly those ids; paste both outputs (only ids starting `test_user_`; never delete any other, never the human's real users). Announce with the filled final-report template (what is wired: write, read, stream, identity, sensitive data, tests; test data removed and what could not be; what was skipped and why; open decisions; bugs not fixed; a line "Nothing was committed" and the list of files created and changed). Then, only if verify passed, `<cli> auth logout` last, after every `onboard report`; say it is signed out ONLY if it exits 0 and reports revoked (exit 9 `revocation_pending` means it is still active until expiry: retry, then report it as an open item).

## The implicit path: send all five events every turn

- `user_message` and `assistant_message`: `send_message(event_type=...)`; without the first the turn is not recorded, without the second anticipation never runs.
- `agent_thinking`: `record_thinking(...)`. `tool_call`: `record_tool_call(...)`. `tool_result`: `record_tool_result(...)`, the strongest hint of the next question.

One stream per process: `listen()` at startup, `end_session` when a conversation ends, `stop_listening()` on shutdown. Never hand-set `role` on tool or reasoning events. Never stream a turn and also `memories.create()` the same text. Scope: `user_id` always; `customer_id` only on B2B; `conversation_id` must be a UUID.

## Hard rules

Never guess; `not stated` for gaps; confirm before create; never print, paste or commit the key; never create or delete workspaces or touch billing or members; **never run `git commit`, `git add -A`, `git push`, `git stash` or an amend** (leave changes uncommitted and new files untracked for the human); **never say "production", "prod", "staging" or "environment" about Synap to the human** (for them there is just Synap; use `--env` silently); **never show raw status words** (`building`, `failed`, `b2c`, `no_instance`): translate them with the glossary below (read the docs first for a word not in it); a known defect you caused is fixed or asked about first, never left as a later decision; the human never has to go back to the dashboard once the flow has started. The live docs at https://docs.maximem.ai win over this file.

## Instances in plain words (glossary)

An **instance** is the memory space Synap built for one agent. A key opens exactly one instance (/concepts/memory-scopes.md, "What is an Instance?"). Say:

- `building`, `attempt 2 of 3`: Synap is preparing the memory design from the approved file (15 to 20 minutes; it retries up to three times itself). `ready`: finished. `failed`: not built after three tries; restart from the same file. `awaiting_review`: waiting for the Synap team.
- `b2c`/`equals_customer`: each end user has private memory. `b2b`/`strict`: users belong to a customer organization.
- `onboard status`: `no_instance`, `no_api_key`, `no_ingestion`, `no_retrieval` = nothing created, no key, nothing written, nothing read back yet; `activated` = it works. `no_agent` is not a Synap word; never say it.
