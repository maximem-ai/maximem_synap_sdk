# Onboarding procedure: full text of every step

This is the long form of the procedure that `SKILL.md` summarizes. Where this file and `SKILL.md` differ (the start variants, the integration-path step, the "Done means" list, the Docs read gate, the final-report template), `SKILL.md` wins. Nothing was removed when `SKILL.md` was shortened; read the step you are on here when you need the exact wording, the edge cases, the retry-time rules, the build-state meanings or the required sign-out message.

## Procedure (full text)

**CLI selection (read once).** In this skill `<cli>` means `maximem-synap` from PATH when `maximem-synap --version` reports 0.3.0 or newer (it starts instantly and avoids npx fetching an older published version), otherwise `npx @maximem/synap-cli@latest`. Pick one at the start and use it for every command. The `npx` form needs Node and Python 3.10+ (npx only installs the Python CLI).

**Environment.** If the prompt names an environment, add `--env <name>` to every CLI command (or `export SYNAP_ENV=<name>` in the commands' shell). A one-time code only works against the server that issued it. If the prompt names none, do nothing extra.

**Quick reference (CLI).** Put global flags before the subcommand: `<cli> --output json instances list` (`--json` is an alias only if your CLI accepts it). Ids can be shown truncated in a table: use the full `inst_...` id from `--output json`, never a shortened one. `api-keys create --write-env` writes `SYNAP_API_KEY` and `SYNAP_INSTANCE_ID`, and on a non-production environment also `SYNAP_BASE_URL`, `SYNAP_GRPC_HOST`, `SYNAP_GRPC_PORT` and `SYNAP_GRPC_USE_TLS`: do not add those by hand. Always pass `--env <name>` when the prompt names an environment, always pass `--agent-name <name>` at sign-in, and run CLI commands with `env -u SYNAP_API_KEY` when that variable is set in your shell. Full CLI reference: `reference/dashboard-setup.md`.

The CLI provisions the instance and key, so do it yourself, in this order. **Never guess. If anything is unclear, stop and ask the human.** A wrong guess costs a new instance and 15 to 20 minutes. Wording, failures and resume rules: `reference/onboarding-ask-rules.md`. CLI details: `reference/dashboard-setup.md`.

1. **Sign in.** `<cli> auth login --code <syn_ob_...> --agent-name <name>`. Use the one-time code from the human's prompt. Pass `--agent-name <name>` with your own short product name in lowercase (`claude-code`, `cursor`, `codex`, `windsurf`, or `other`) so the dashboard checklist can say which agent is connected (the CLI also reads `SYNAP_AGENT_NAME`). Missing, expired or used code at this first sign-in is the one case where you say: copy a fresh prompt from the dashboard. Do not fall back to the browser flow silently. The key lasts 7 days, fixed, and cannot be renewed (never run `auth refresh` for it). Within 7 days a new session resumes from `onboard status` and the profile; after expiry ask the human for a fresh prompt.
2. **Check state.** `... onboard status`. Resume from the first unfinished step; re-running the prompt must be safe, including in a new session (the profile is on disk).

**Step 0: learn Synap first (required; do it after step 2 and before step 3).** Read in full, not skimmed: /getting-started/quickstart, /concepts/memory-model-cheat-sheet, /concepts/memory-scopes, /concepts/how-ingestion-works, /concepts/retrieval-modes, /concepts/real-time-anticipation (docs.maximem.ai, `.md` for clean text). Once step 3 names the framework, read its page at /integrations/<name> in full too, before step 6. Then tell the human, in the session, four lines on what you understood: (1) the scoping model (`user_id` and `customer_id` by B2C or B2B), (2) the three operations (write, read, live stream), (3) why the live stream matters, (4) the build/ready rule (nothing runs against the instance until `instances wait` is ready). A misunderstanding should surface here, not after the code is written.

3. **Read the repo.** Detect the framework (`reference/frameworks/_index.md`) and what the agent does. Infer only what the code supports. Read next: `reference/frameworks/<name>.md` and docs.maximem.ai/integrations/<name>.
4. **Ask the human, one question at a time:** who uses the agent (B2C or B2B; immutable once the instance exists), what identifies a returning person in this app (a stable user id; if there is none, memory can only be per session), compliance and sensitive data, what matters most to remember, what must never be stored (read next: docs.maximem.ai/concepts/memory-scopes). Show the evidence you found, and still ask. While waiting run `onboard ask "<question>"`. Why you ask instead of guessing: B2C or B2B cannot be changed after the instance exists, and a wrong guess costs a new instance and 15 to 20 minutes. The other answers decide what memory keeps, so a guess shows up later as the wrong things remembered. If the answer means memory cannot serve the approved goal (for example a session id as the user id while the goal is remembering returning users), say so plainly before approval and ask again. If the human names health, financial, children's or other personal data, read /guides/pii-protection first (rules in `reference/onboarding-ask-rules.md`).
5. **Draft the use-case** from `instances template`, every unanswered field literally `not stated` (`reference/use-case-markdown.md`; docs.maximem.ai/concepts/memory-architecture). Show it. Get explicit approval; it cannot be edited after creation. Run `onboard report use_case_drafted done`, then `use_case_approved done`. Why the human approves the exact text: the use-case cannot be edited after the instance is created, so what they approve is final. Show the EXACT file you will upload: print its full contents in chat (or give its path and show the full text), and upload exactly that file, never a longer or different one. At approval run `shasum -a 256 usecase.md` and quote the hash; if the CLI prints a sha256 on create it must match. If you change one character after approval, ask again.
6. **Create the instance** only after telling the human it usually takes 15 to 20 minutes, and they agree. `instances create --name ... --relationship b2c|b2b --from-file usecase.md`. **Do not wait for the build.** Run `onboard report integrating in_progress`, then install the SDK and write the integration while the build runs (but do not run it against the instance yet). Why you do not use it yet: the server refuses memory calls until the build is ready, and a half-built instance would store memories with the wrong configuration.
7. **Integrate.** Follow `reference/sdk-setup.md` (docs: /setup/installation, /setup/authentication, /sdk/ingestion, /sdk/context-fetch, /sdk/error-handling) and the framework file. Wire the live stream (`reference/streaming.md`; docs: /concepts/real-time-anticipation); in a long-lived process it is part of the integration, not an extra.
   **Docs checkpoint loop (required).** Before you write each Synap call, open that method's page under /sdk-reference/ (for example /sdk-reference/memories/create or /sdk-reference/context/user-fetch). After writing it, re-read the page and check every parameter, the scope rule (`user_id` always; `customer_id` only on a B2B instance, per whoami), the mode, and the errors it can raise. Before wiring the live stream re-read /concepts/real-time-anticipation and /sdk-reference/instance/listen. Before step 9 print in chat a **"Docs read" list**: every page you actually OPENED (read, not just downloaded or curled; a page you did not read does not count) with one line on what it changed in the code. Step 9 is gated on these being opened: /guides/production-checklist, /patterns/graceful-degradation, /sdk-reference/errors and each /sdk-reference method page you used. Compare them with what you wrote. If the docs and this skill disagree, the docs win; tell the human which one you followed.
8. **Save the key.** `api-keys create -i <instance_id> --write-env`, then `onboard report env_written done`. It prints only a masked key. Never print, paste or commit the full key. Why `.env` and never printed: anything you print stays in this transcript and its logs, while `.env` stays on this machine and out of git. **Protect the build window:** the project's own tests or dev server may load `.env` and call Synap while the build is still running. Run the project's tests with `env -u SYNAP_API_KEY ...` (or the integration disabled) until verify has passed, and tell the human why: a memory call on a building instance is refused and the write may be lost.
9. **Wait, then verify.** `instances wait <id>` must report ready first. Run it in the BACKGROUND (redirect its output to a log file, then poll the log or `<cli> onboard status`) so the human can keep talking to you; the build usually takes 15 to 20 minutes (measured: 14m45s and about 20m). It prints, for example, "attempt 2 of 3, about 6 min left" (meaning of each state below). Then run `python scripts/verify_synap.py > verify.out 2>&1; echo "exit=$?"` (no pipe, so you see the real exit code) and paste the WHOLE of verify.out unedited, including every `[WARN]` line; a WARN is reported and explained, never dropped. It ends with `RESULT: PASS` or `RESULT: FAIL <reason>`, then `EXIT CODE: <n>`. A failure is reported as a failure with the reason, never as done. Why recall: only a real write that comes back proves the whole path works.
10. **Announce the result in the session:** what was created, the verbatim verify output, every file you changed, what the human still has to do. Optionally add "view it in your dashboard"; never as a step.
11. **Sign the setup key out, as the LAST step, only if verify passed (never if it failed).** Send every `onboard report` event first: after logout the resume path is gone. Then run `<cli> auth logout`. Only when it exits 0 and reports the key revoked, end the announcement with: "I signed the setup key out. It only existed to set things up and was stored in ~/.config/synap on this machine; it is revoked, so it can no longer be used. Your app keeps working with its own key in .env. If you need the CLI again, run `maximem-synap auth login` or ask for a new prompt." If it fails (for example 403 or no network), say so plainly with the error and do not claim it signed out. Exit code 9 (`revocation_pending`) means the CLI could not revoke the key after 3 tries and kept the local profile marked pending: the key is STILL ACTIVE until its expiry (7 days at most; it can read and create instances and keys). Rerun `auth logout` once or twice; if it is still pending, tell the human plainly that the key stays active until its expiry and that they can revoke it on the dashboard API keys page, and put it in the final report as an OPEN ITEM, not as done. `--json` output has `revoked` and `pending`. If verify failed, keep the key: you need it to rebuild or resume.

**Until `instances wait` reports ready, run no ingestion or retrieval at all, including `verify_synap.py`.** Why: the server refuses them while the build runs, and a half-built instance would store memories with the wrong configuration. A refused call is HTTP 409 `instance_not_ready`. Handle BOTH forms: newer SDKs raise `InstanceNotReadyError` (fields `retry_after_seconds`, `from_cooldown`, `instance_id`; the SDK tells you how long to wait); older SDKs, including the published 0.5.16, raise a `ConflictError` whose message says the memory architecture is still being built. Catch the typed class first, then check the `ConflictError` message. Never loop inside the call. Examples: `reference/sdk-setup.md`. Tell the human their own app gets it too until the build finishes. Write the integration so a read that gets it logs and continues without memory, and a write that gets it is retried later (`reference/sdk-setup.md`).

**What the retry time means.** `retry_after_seconds` is how long Synap says to wait before asking again (30 to 300 s). WAIT that long, tell the human how long ("the memory architecture is still being built, waiting 2 minutes"), then check once. Never retry in a loop: during the wait the SDK refuses locally (`from_cooldown` true, no network call), so a loop only burns time and changes nothing.

**What the build states mean** (shown by `instances wait`): "attempt n of 3, about N min left" = running normally; if a build dies Synap restarts it by itself, up to 3 attempts, and you do nothing. "taking longer than usual" = past the usual 15 to 20 minutes but still alive: keep waiting and tell the human; if `instances wait` times out (exit 7), run it once more, then ask the human whether to keep waiting. "failed" (exit 1, or 409 `instance_build_failed`) = all attempts failed: tell the human the reason in one line, then run `maximem-synap instances rebuild <instance_id>` (it re-runs from the stored use-case, nothing to re-approve; at most 3 rebuilds per 24 hours) and wait again. Ask the human first only if the rebuild is refused (429 limit, 409) or a rebuild fails too.

**CLI and runtime keys do not mix.** If `SYNAP_API_KEY` (the runtime key from the project's `.env`) is set in your shell, CLI calls fail with 401 or 403. Run CLI commands with `env -u SYNAP_API_KEY <cli> ...`, or `unset SYNAP_API_KEY` first. Run `verify_synap.py` with the key set, as it needs it.

Hard rules: the human never has to go back to the dashboard (every failure has an in-session recovery, see `reference/onboarding-ask-rules.md`); never guess; write `not stated` for gaps; confirm before create; never create or delete workspaces, touch billing or members; never print or commit the key. Integration code reads `SYNAP_API_KEY` from the environment, so you can write it before the key exists; just do not run it until step 8 is done.
