# Onboarding procedure: full text of every step

This is the long form of the procedure that `SKILL.md` summarizes. Where this file and `SKILL.md` differ (the start variants, the integration-path step, the "Done means" list, the Docs read gate, the final-report template), `SKILL.md` wins. Nothing was removed when `SKILL.md` was shortened; read the step you are on here when you need the exact wording, the edge cases, the retry-time rules, the build-state meanings or the required sign-out message.

## Procedure (full text)

**CLI selection (read once).** In this skill `<cli>` means `maximem-synap` from PATH when `maximem-synap --version` reports 0.3.3 or newer (it starts instantly and avoids npx fetching an older published version), otherwise `npx @maximem/synap-cli@latest`. Pick one at the start and use it for every command. The `npx` form needs Node and Python 3.10+ (npx only installs the Python CLI).

**Environment (never say this word to the human).** If the prompt names an environment, add `--env <name>` to every CLI command (or `export SYNAP_ENV=<name>` in the commands' shell). A one-time code only works against the server that issued it. If the prompt names none, do nothing extra.

**Quick reference (CLI).** Put global flags before the subcommand: `<cli> --output json instances list` (`--json` is an alias only if your CLI accepts it). Ids can be shown truncated in a table: use the full `inst_...` id from `--output json`, never a shortened one. `api-keys create --write-env` writes `SYNAP_API_KEY` and `SYNAP_INSTANCE_ID` (or `SYNAP_API_KEY_<NAME>` and `SYNAP_INSTANCE_ID_<NAME>` with `--env-suffix NAME`), and when the CLI is pointed at another server also `SYNAP_BASE_URL`, `SYNAP_GRPC_HOST`, `SYNAP_GRPC_PORT` and `SYNAP_GRPC_USE_TLS`: do not add those by hand. Always pass `--env <name>` when the prompt names an environment, always pass `--agent-name <name>` at sign-in, and run CLI commands with `env -u SYNAP_API_KEY` when that variable is set in your shell. Full CLI reference: `reference/dashboard-setup.md`.

The CLI provisions the instance and key, so do it yourself, in this order. **Never guess. If anything is unclear, stop and ask the human.** A wrong guess costs a new instance and 15 to 20 minutes. Wording, failures and resume rules: `reference/onboarding-ask-rules.md`. CLI details: `reference/dashboard-setup.md`.

1. **Sign in.** `<cli> auth login --code <syn_ob_...> --agent-name <name>`. Use the one-time code from the human's prompt. Pass `--agent-name <name>` with your own short product name in lowercase (`claude-code`, `cursor`, `codex`, `windsurf`, or `other`) so the dashboard checklist can say which agent is connected (the CLI also reads `SYNAP_AGENT_NAME`). Missing, expired or used code at this first sign-in is the one case where you say: copy a fresh prompt from the dashboard. Do not fall back to the browser flow silently. The key lasts 7 days, fixed, and cannot be renewed (never run `auth refresh` for it). Login prints the profile name for this session: see "Sessions and profile pin" below. Within 7 days a new session keeps the sign-in (the profile is on disk), but it still follows step 2: it trusts only what it reported itself; after expiry ask the human for a fresh prompt.
2. **Check state.** `<cli> onboard status` shows THIS session's own steps and question, then a read-only list of OTHER sessions in the workspace (tool, agent, state, instance, waiting). Trust only the steps you reported yourself in this session; the other sessions are someone else's work: never act on them, never answer their questions, and never skip drafting, approval or creation because they look done. Re-running the prompt is safe: the profile and the repo are on disk.
2b. **What already exists (right after step 2, before Step 0 and before drafting).** Run `<cli> instances list --json` and tell the human in plain words what is in the workspace: for each instance its name, what it is for if known, and whether it is ready, still being built or failed (translate with `reference/instances-explained.md`; never show the raw words). If there are none, say so and go on. If there are some, ask ONE question, with your recommendation and tip (read /concepts/agent-topologies first): reuse an existing instance, or create a new one. Recommend reuse only if that instance is for THIS agent: one instance serves one agent, so an instance made for a different agent is not a candidate. Reuse follows the existing-instance variant (`reference/no-code-path.md`, branch C and E): skip drafting, approval, creation and (if it is ready) the build wait; still do Step 0, the identity question, the depth and path choice, the read path, verify and the test-data cleanup. If the human picks a new instance, continue at step 3.

**Step 0: learn Synap first (required; do it after step 2 and before step 3).** Read in full, not skimmed: /getting-started/quickstart, /concepts/memory-model-cheat-sheet, /concepts/memory-scopes, /concepts/how-ingestion-works, /concepts/retrieval-modes, /concepts/real-time-anticipation (docs.maximem.ai, `.md` for clean text). Once step 3 names the framework, read its page at /integrations/<name> in full too, before step 6. Then tell the human, in the session, four lines on what you understood: (1) the scoping model (`user_id` and `customer_id` by B2C or B2B), (2) the three operations (write, read, live stream), (3) why the live stream matters, (4) the build/ready rule (nothing runs against the instance until `instances wait` is ready). A misunderstanding should surface here, not after the code is written.

3. **Read the repo.** Detect the framework (`reference/frameworks/_index.md`) and what the agent does. Infer only what the code supports. Read next: `reference/frameworks/<name>.md` and docs.maximem.ai/integrations/<name>.
4. **Ask the human, one question at a time:** who uses the agent (B2C or B2B; chosen when the instance is created), what identifies a returning person in this app (a stable user id; if there is none, memory can only be per session), compliance and sensitive data, what matters most to remember, what must never be stored (read next: docs.maximem.ai/concepts/memory-scopes). Show the evidence you found, and still ask. While waiting run `onboard ask "<question>"`. Why you ask instead of guessing: B2C or B2B is chosen at creation (a later change goes through the email request below), and a wrong guess costs a new instance and 15 to 20 minutes. If the repo has more than one agent (several agent classes, services, personas, bots), ask first which agent gets memory now and say that further agents each need their own instance later. Right after the answer (with one agent, right after you read the repo), and before creating the instance, run `<cli> onboard target "<AgentName>"`: see "Sessions and profile pin". Every question carries your recommendation (what you suggest and why, from the repo) and a tip on how Synap uses the answer, written only after you read the docs page(s) named for that question in `reference/onboarding-ask-rules.md`. The other answers decide what memory keeps, so a guess shows up later as the wrong things remembered. If the answer means memory cannot serve the approved goal (for example a session id as the user id while the goal is remembering returning users), say so plainly before approval and ask again. If the human names health, financial, children's or other personal data, read /guides/pii-protection first (rules in `reference/onboarding-ask-rules.md`).
5. **Draft the use-case** from `instances template`, every unanswered field literally `not stated` (`reference/use-case-markdown.md`; docs.maximem.ai/concepts/memory-architecture). Show it. Get explicit approval; once the file is sent, it can only be changed by making a request through email to gaurav@maximem.ai. Run `onboard report use_case_drafted done`, then `use_case_approved done`. Why the human approves the exact text: the human cannot edit it themselves after it is sent (it can only be changed by making a request through email to gaurav@maximem.ai), so say that when you ask. Show the EXACT file you will upload: print its full contents in chat (or give its path and show the full text), and upload exactly that file, never a longer or different one. At approval run `shasum -a 256 usecase.md` and quote the hash; if the CLI prints a sha256 on create it must match. If you change one character after approval, ask again.
6. **Create the instance** only after telling the human it usually takes 15 to 20 minutes, and they agree. `instances create --name ... --relationship b2c|b2b --from-file usecase.md`. If it returns HTTP 409 `instance_name_taken`, the workspace already has an instance with that name (the server is about to refuse duplicate names; the code is handled only if it is returned): say so plainly and ask the human whether to reuse that instance (only if it is for this agent) or choose another name; pick nothing yourself. A 409 `instance_limit_reached` (the workspace or this session hit its instance limit) or 429 `instance_create_rate_limited`: stop, tell the human the limit and count from the message, and ask whether to reuse an existing instance or contact support. Never retry, delete instances to make room, or use another key or workspace. **Do not wait for the build.** Run `onboard report integrating in_progress`, then install the SDK and write the integration while the build runs (but do not run it against the instance yet). Why you do not use it yet: the server refuses memory calls until the build is ready, and a half-built instance would store memories with the wrong configuration.
7. **Integrate.** Follow `reference/sdk-setup.md` (docs: /setup/installation, /setup/authentication, /sdk/ingestion, /sdk/context-fetch, /sdk/error-handling) and the framework file. Wire the live stream (`reference/streaming.md`; docs: /concepts/real-time-anticipation); in a long-lived process it is part of the integration, not an extra.
   **Docs checkpoint loop (required).** Before you write each Synap call, open that method's page under /sdk-reference/ (for example /sdk-reference/memories/create or /sdk-reference/context/user-fetch). After writing it, re-read the page and check every parameter, the scope rule (`user_id` always; `customer_id` only on a B2B instance, per whoami), the mode, and the errors it can raise. Before wiring the live stream re-read /concepts/real-time-anticipation and /sdk-reference/instance/listen. Before step 9 print in chat a **"Docs read" list**: every page you actually OPENED (read, not just downloaded or curled; a page you did not read does not count) with one line on what it changed in the code. Step 9 is gated on these being opened: /guides/production-checklist, /patterns/graceful-degradation, /sdk-reference/errors and each /sdk-reference method page you used. Compare them with what you wrote. If the docs and this skill disagree, the docs win; tell the human which one you followed.
8. **Save the key.** `api-keys create -i <instance_id> --write-env`, then `onboard report env_written done`. It prints only a masked key. Never print, paste or commit the full key. This setup key can mint keys for, and rebuild, ONLY instances this session created (see "Setup-key limits"). A key opens exactly one instance, so keep one key per instance. If the project will have more than one Synap instance, or you are not sure (ask), add `--env-suffix NAME` (CLI 0.3.3 and newer): `api-keys create -i <id> --write-env --env-suffix NAME`. Name it after the instance or the agent (letters, digits, underscore; the CLI upper-cases it). It writes `SYNAP_API_KEY_<NAME>` and `SYNAP_INSTANCE_ID_<NAME>` and leaves every other instance's lines alone; without it a second instance would take over `SYNAP_API_KEY`, so the CLI refuses with exit 6 unless you add a suffix or `--force`. The app must read the matching variable and pass the key explicitly, and `verify_synap.py --suffix NAME` verifies that instance (`reference/sdk-setup.md`, "Several instances"). Why `.env` and never printed: anything you print stays in this transcript and its logs, while `.env` stays on this machine and out of git. **Protect the build window:** the project's own tests or dev server may load `.env` and call Synap while the build is still running. Run the project's tests with `env -u SYNAP_API_KEY ...` (or the integration disabled) until verify has passed, and tell the human why: a memory call on a building instance is refused and the write may be lost.
9. **Wait, then verify.** `instances wait <id>` must report ready first. Run it in the BACKGROUND (redirect its output to a log file, then poll the log or `<cli> onboard status`) so the human can keep talking to you; the build usually takes 15 to 20 minutes (measured: 14m45s and about 20m). It prints, for example, "attempt 2 of 3, about 6 min left" (meaning of each state below). Then run `python scripts/verify_synap.py > verify.out 2>&1; echo "exit=$?"` (add `--suffix NAME` when the key was written with `--env-suffix NAME`; no pipe, so you see the real exit code) and paste the WHOLE of verify.out unedited, including every `[WARN]` line; a WARN is reported and explained, never dropped. It ends with `RESULT: PASS` or `RESULT: FAIL <reason>`, then `EXIT CODE: <n>`. A failure is reported as a failure with the reason, never as done. Why recall: only a real write that comes back proves the whole path works.
10. **Clean up test data, then announce the result in the session.** Test ids: every test or probe user id the coding agent creates (the project's own tests, the sentinel check, verify) uses ONE convention, `test_user_<purpose>_<8 random chars>` (for example `test_user_verify_a1b2c3d4`; `python scripts/cleanup_test_data.py --suggest-id <purpose>` prints one). `verify_synap.py` follows it and prints its two ids (`[WRITE]`, `[PROBE]`, `[TEST IDS]`). Write down every id you used. Before sign-out, for exactly those ids, run `python scripts/cleanup_test_data.py --user-id <id> [--user-id <id> ...] --dry-run`, read it, then run the same command without `--dry-run`, and paste both outputs. It only ever touches ids that start with `test_user_` (it refuses anything else), verifies afterwards and ends with `RESULT: CLEAN` or `RESULT: INCOMPLETE`, and lists what it cannot remove (for example recorded conversation turns, customer-scope memories, usage and billing rows). On B2B add `--customer-id`. Never delete any id that does not start with `test_user_`, and never touch the human's own real users. Report in the final report what was removed and what could not be (the script prints the residue). A delete-data-by-scope SDK method is being built; when the SDK offers it, use it instead of the script. Then announce: what was created, the test data removed and what could not be, the verbatim verify output, every file you changed, what the human still has to do, a line "Nothing was committed" and the list of files created and changed. Optionally add "view it in your dashboard"; never as a step.
11. **Sign the setup key out, as the LAST step, only if verify passed (never if it failed).** Verify comes BEFORE `auth logout` (see "What finished means"). Send every `onboard report` event first: after logout the resume path is gone. Then run `<cli> auth logout`. Only when it exits 0 and reports the key revoked, end the announcement with: "I signed the setup key out. It only existed to set things up and was stored in ~/.config/synap on this machine; it is revoked, so it can no longer be used. Your app keeps working with its own key in .env. If you need the CLI again, run `maximem-synap auth login` or ask for a new prompt." If it fails (for example 403 or no network), say so plainly with the error and do not claim it signed out. Exit code 9 (`revocation_pending`) means the CLI could not revoke the key after 3 tries and kept the local profile marked pending: the key is STILL ACTIVE until its expiry (7 days at most; it can read and create instances and keys). Rerun `auth logout` once or twice; if it is still pending, tell the human plainly that the key stays active until its expiry and that they can revoke it on the dashboard API keys page, and put it in the final report as an OPEN ITEM, not as done. `--json` output has `revoked` and `pending`. If verify failed, keep the key: you need it to rebuild or resume.

**Until `instances wait` reports ready, run no ingestion or retrieval at all, including `verify_synap.py`.** Why: the server refuses them while the build runs, and a half-built instance would store memories with the wrong configuration. A refused call is HTTP 409 `instance_not_ready`. Handle BOTH forms: newer SDKs raise `InstanceNotReadyError` (fields `retry_after_seconds`, `from_cooldown`, `instance_id`; the SDK tells you how long to wait); older SDKs, including the published 0.5.16, raise a `ConflictError` whose message says the memory architecture is still being built. Catch the typed class first, then check the `ConflictError` message. Never loop inside the call. Examples: `reference/sdk-setup.md`. Tell the human their own app gets it too until the build finishes. Write the integration so a read that gets it logs and continues without memory, and a write that gets it is retried later (`reference/sdk-setup.md`).

**What the retry time means.** `retry_after_seconds` is how long Synap says to wait before asking again (30 to 300 s). WAIT that long, tell the human how long ("the memory architecture is still being built, waiting 2 minutes"), then check once. Never retry in a loop: during the wait the SDK refuses locally (`from_cooldown` true, no network call), so a loop only burns time and changes nothing.

**What the build states mean** (shown by `instances wait`): "attempt n of 3, about N min left" = running normally; if a build dies Synap restarts it by itself, up to 3 attempts, and you do nothing. "taking longer than usual" = past the usual 15 to 20 minutes but still alive: keep waiting and tell the human; if `instances wait` times out (exit 7), run it once more, then ask the human whether to keep waiting. "failed" (exit 1, or 409 `instance_build_failed`) = all attempts failed: tell the human the reason in one line, then run `maximem-synap instances rebuild <instance_id>` (it re-runs from the stored use-case, nothing to re-approve; at most 3 rebuilds per 24 hours) and wait again. Ask the human first only if the rebuild is refused (429 limit, 409) or a rebuild fails too.

**CLI and runtime keys do not mix.** If `SYNAP_API_KEY` (the runtime key from the project's `.env`) is set in your shell, CLI calls fail with 401 or 403. Run CLI commands with `env -u SYNAP_API_KEY <cli> ...`, or `unset SYNAP_API_KEY` first. Run `verify_synap.py` with the key set, as it needs it.

## Sessions and profile pin (CLI 0.3.3 and newer)

One pasted prompt is one session. Several agents can share one machine and one workspace, so the CLI's "active profile" may be another agent's.

- **Pin.** `auth login --code` prints the profile name for this session. Put `--profile <name>` before the subcommand of EVERY CLI command (`<cli> --profile <name> onboard status`). Your shell does not keep environment variables between calls, so `SYNAP_PROFILE=<name>` works only if your shell persists.
- **Never** log out, refresh, delete or use a profile that is not yours (`auth list` names every profile).
- **Refusal.** With two setup sessions on the machine and no pin, a command stops with exit 2 `profile_not_pinned`: "More than one setup session is saved on this machine (<names>) and no profile is pinned, so this command might act as the wrong agent. Nothing was done." Read the names in it, pick the one printed by YOUR login, and run the command again with `--profile <yours>`. `auth logout` refuses the same way: log out with `auth logout --profile <yours>`.
- **Target.** `<cli> --profile <p> onboard target "<AgentName>"`: the CLIENT's agent you are giving memory (for example `BillingAgent`; 1 to 60 characters, plain one-line text, no `<` or `>`, no control or invisible characters), never an instance id. It names this session on the dashboard ("Claude Code · BillingAgent"). Run it right after the human answers "which agent gets memory" and before `instances create`; with one agent in the repo use that agent's name. Running it again changes the name; it affects this session only.
- **Status.** `onboard status` lists the OTHER sessions read-only. They carry labels and state only. They are someone else's work: do not act on them or answer their questions, and do not copy their instance ids into this project.

## Setup-key limits

This session's setup key can mint API keys for, and rebuild, ONLY instances this session created. It can read every instance. For an instance you are reusing (the reuse path from `instances list`), `api-keys create` fails with 403 `instance_not_created_by_this_session` (exit 5). The CLI says: "This setup key only manages instances this session created itself, and <instance id> was not created by it." with the hint "Ask the human to create the API key for that instance in the dashboard (API keys page) and put it into the project's .env themselves. Do not look for another way around it." `instances rebuild` of such an instance is refused the same way. Say to the human, plainly: "This setup key only manages instances this session created itself. Please create the API key for <instance name> in the dashboard (API keys page) and add it to the project's .env as <VARIABLE>; I will not look for another way around it." Name the exact variable (`SYNAP_API_KEY`, or `SYNAP_API_KEY_<NAME>` with a suffix). Never ask for the key in chat. Continue with the rest of the work (Step 0, the read path, tests with `env -u SYNAP_API_KEY`) and resume the key-dependent steps (verify) once the variable exists in `.env`.

## What finished means

The dashboard counts a session as finished only when the server has seen a first memory written AND a successful retrieval for its instance, and `verify_synap.py` produces both. Signing out earlier shows "ended before verification" on the dashboard (signing out never finishes a session). So run verify BEFORE `auth logout`, and if you cannot verify, say so in the final report. The final report carries the line: "Dashboard shows finished only after the first memory and a useful recall: <yes/no>".

Hard rules: the human never has to go back to the dashboard (every failure has an in-session recovery, see `reference/onboarding-ask-rules.md`); never guess; write `not stated` for gaps; confirm before create; never create or delete workspaces, touch billing or members; never print or commit the key; Never run `git commit`, `git add -A`, `git push`, `git stash` or a commit `--amend`: leave every change uncommitted and every new file untracked, for the human to review and commit. Never say "production", "prod", "staging" or "environment" about Synap to the human: for them there is just Synap (if the prompt names an environment, use it silently with `--env`). Never show raw status words (`building`, `failed`, `attempt 2 of 3`, `b2c`, `no_instance`) to the human: translate them with `reference/instances-explained.md`; if a word is not there, read the docs first and say it simply. Integration code reads `SYNAP_API_KEY` from the environment, so you can write it before the key exists; just do not run it until step 8 is done.
